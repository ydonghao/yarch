# 微前端开发规约（v1.0 已定稿）

> **状态：已定稿**（2026-09-07 经 MF0-MF7 决策清单拍板，`contract/web/` 前端规约层首份）。供人阅读、供 AI 作为规范上下文使用。
> 等级：**【强制】**违反即缺陷；**【推荐】**默认遵守、评审后可豁免；**【参考】**正向引导。
> 条文**载器无关**（micro-app / qiankun / Module Federation 均须满足）；载器分档唯一登记于 [../README.md](../README.md)「关键架构决策登记表」，换档不改条文。
> 约束对象：微前端体系内**基座与子应用彼此之间的契约**。单应用工程（`npm create @yarch/admin` 生成物）不受本规约约束，仅在接入微前端时适用。

## 一、适用范围与角色定义

1. 【强制】微前端由两类工程组成，职责不得互换：**基座（base）**全局唯一，承载布局、菜单、登录态、路由分发、全局错误兜底；**子应用（sub-app）**N 个，每个对应一个业务域（对齐后端一个服务/领域的边界），只做域内页面。
2. 【强制】一个项目一个基座；子应用不得嵌套再当基座（嵌套微前端一律评审否决——复杂度不可控）。
3. 【强制】子应用必须同时具备两种运行形态：**独立运行**（本地 dev 单独起服务）与**集成运行**（被基座加载）；只会集成、不会独立运行的子应用视为缺陷（见十一）。
4. 【参考】选型判断：单团队单仓库优先 pnpm workspace 单应用分包，**不得为微前端而微前端**；微前端仅适用于多团队独立发版、存量技术栈整合两类场景。

## 二、应用命名与登记

1. 【强制】应用名（基座与子应用统一）格式 `^[a-z][a-z0-9-]{1,31}$`，由「服务名-用途/域」两段及以上构成，**首段必须是 [../registry.md](../registry.md) 已登记的服务名**，不得直接使用纯服务名——前端应用名是服务名在前端空间的延伸。

```
正例：ysaas-console（基座）、ysaas-billing（子应用）——首段 ysaas 已登记
反例：billing（首段无登记服务名，共享域名下必冲突）
      ysaas（纯服务名，与服务名本身混淆）
```

2. 【强制】应用名登记于 [../registry.md](../registry.md) 前端应用名登记表，**一名三用**：

| 用途 | 规则 | 正例 |
|---|---|---|
| 路由前缀 | `/{应用名}/...` | `/ysaas-billing/invoices` |
| storage key 前缀 | `{应用名}:...`（冒号分层，同 [../infra/redis.md](../infra/redis.md) key 哲学） | `ysaas-billing:filter-state` |
| 自定义事件名前缀 | `{应用名}:{动词-名词}` | `ysaas-billing:export-done` |

3. 【强制】应用名一经登记并产生路由前缀/storage key/事件名即冻结；改名 = 契约破坏性变更，走 registry 变更评审。
4. 【强制】同项目基座与全部子应用互不重名；跨项目不得重名（同域名下 storage 与事件空间物理共享）。

## 三、基座与子应用职责分界

1. 【强制】判断标准：去掉全部子应用后基座仍能运行——登录、菜单框架、404、全局错误页齐全；做不到即职责分配缺陷。
2. 【强制】基座负责：布局与外壳、菜单/导航树、登录态与 token 管理、路由分发、全局 loading 与错误兜底、主题与 UI 档定义。
3. 【强制】子应用禁做：注册全局组件、篡改基座菜单、直连基座内部 store、域外全局副作用（改 `document.title` 为唯一豁免项）。
4. 【强制】菜单与路由声明式注册：子应用构建产物 manifest 携带路由表与菜单元数据，基座读取装配；基座禁硬编码子应用内部路由。
5. 【推荐】子应用间业务复用走 npm 包（版本化），禁跨子应用源码直接 import——微前端边界不是代码复用边界。

## 四、路由规范

1. 【强制】子应用路由前缀 = 应用名（二-2）；基座按前缀分发，全站 URL 无方言。
2. 【强制】子应用不得感知被挂载的完整 URL：路由 base/basename 由基座挂载时**注入**；独立运行时从环境变量取同值（十一-2 供给层）。
3. 【强制】跨应用跳转必须走**导航端口**（`@yarch/contract` navigator，基座注册实现），禁 `window.location.href` 整页刷新跳转（丢失基座状态与登录上下文）；应用内跳转用框架路由。
4. 【强制】路径段命名 kebab-case（对齐 [../api/rest-conventions.md](../api/rest-conventions.md)）：小写短横线，禁驼峰/下划线。
5. 【强制】基座必须兜底未匹配路由（404 页）与子应用加载失败页（含重试入口），禁白屏。
6. 【推荐】路由前缀调整按二-3 破坏性变更评审，并联动基座 manifest 与菜单元数据同批发布。

## 五、生命周期契约

1. 【强制】子应用必须具备三段生命周期语义：**初始化（bootstrap）/ 挂载（mount）/ 卸载（unmount）**——single-spa 系载器以导出函数提供，WebComponent 系载器以元素生命周期提供；形式由模板档固化，语义对所有载器一致。
2. 【强制】`mount` 完成前 UI 态由基座持有（loading 骨架）；`unmount` 必须彻底清理：定时器、window/document 监听、动态插入的 DOM——卸载后留全局残留即内存泄漏缺陷。
3. 【强制】mount/unmount 幂等：应用间来回切换不崩、不重复注册监听。
4. 【强制】子应用加载失败（网络/版本不匹配）不得影响基座与其他子应用：错误隔离在边界内，基座出错误页并保留重试。
5. 【推荐】`props` 下发收敛为最小集：容器节点、路由 base、导航端口实例、用户上下文与取 token 函数、主题 token——禁把基座整个 store 实例扔给子应用。

## 六、样式隔离纪律

1. 【强制】**同一微前端体系 UI 档唯一**（semi/antd/arco 三档之一，基座定档）：全部子应用同档；跨档混用（基座 semi + 子应用 antd）一律否决——体积翻倍且视觉割裂。
2. 【强制】子应用必须启用隔离机制（载器 scoped CSS/shadow DOM，或工程侧 CSS Modules/Scoped），选哪层由模板档固化，业务工程不自选、不关闭。
3. 【强制】弹层组件（Modal/Select/Tooltip 等默认挂 body 的）必须指定挂载容器为当前应用容器（getContainer 类机制），防样式逃逸到基座 document。
4. 【强制】全局样式（reset/variables）只允许基座注入一份；子应用禁引全局 reset。
5. 【强制】主题与设计 token 从基座下发（props 或 CSS Variables）；子应用禁自带第二套主题定义。
6. 【推荐】z-index 分段登记：基座布局层 < 子应用内容层 < 全局弹层（基座持有），防层高竞赛。

## 七、JS 沙箱与全局纪律

1. 【强制】子应用运行在载器沙箱内；关闭沙箱必须评审豁免并在业务仓 `docs/waivers.md` 登记。
2. 【强制】`window` 挂载禁令：子应用禁向 window 写自定义属性（全局函数/变量/第三方 SDK 实例）；确需全局单例的依赖走八-2 共享口径，经基座注册。
3. 【强制】localStorage/sessionStorage key 必须带应用名前缀（二-2）；裸 key（`token`、`userInfo` 直写）= 跨应用覆写事故。
4. 【强制】对 window/document 的全局监听（resize/scroll/keydown 等）必须在 unmount 成对移除（与五-2 同源）。
5. 【强制】cookie 禁承载业务数据（基座域名共享，cookie 无应用隔离）；登录态走十。
6. 【推荐】第三方脚本（统计/地图/播放器）由使用方子应用按需加载并自清理，禁基座预载全部。

## 八、公共依赖共享

1. 【强制】`@yarch/contract` **运行时单例**：整个体系（基座 + 全部子应用）只允许一份实例，由基座注册共享；子应用私带第二份即缺陷——两份实例 = 两个 `ApiError` 类，`instanceof` 全失效。
2. 【强制】框架运行时共享分两档登记：react/react-dom/react-router（或 vue/vue-router）由基座统一提供版本，子应用声明 peerDependencies 不打包；其余依赖默认**不共享**（各自打包，体积换隔离）。
3. 【强制】共享依赖版本升级由基座统一发起（升版 = 全体系回归）；子应用禁锁定与基座冲突的私有版本。
4. 【推荐】共享候选判定：体积 >200KB 且全体系使用（如图表库）才入共享清单；清单在基座仓登记，其余一律各自打包。
5. 【参考】Module Federation 场景档下 remotes/exposes 模块名与版本协商在基座仓登记成表，视同 API 契约管理。

## 九、通信规范

1. 【强制】通信仅三条通道，禁第四条：**props 下行**（基座→子应用，挂载注入，见五-5）；**事件上行/广播**（子应用→基座、子应用↔子应用，事件名带应用名前缀，payload 为可序列化 JSON）；**URL 状态**（跨应用共享的浅状态走 query/hash，配合四-3 导航端口）。
2. 【强制】子应用之间禁直调内部实现（import 兄弟应用的 store/函数）；兄弟通信只能经基座事件总线或后端 API。
3. 【强制】事件名格式 `{应用名}:{动词-名词}`（如 `ysaas-billing:export-done`）；裸事件名（`refresh`）多应用同名互踩，禁。
4. 【强制】事件处理方异常不得中断发布方：事件总线的 try/catch 兜底归基座底座包职责。
5. 【推荐】全局状态归基座且只放登录态/主题/布局三类；业务状态归子应用——业务状态提升到基座是基座腐化的起点。

## 十、登录态与 trace 贯穿

1. 【强制】token 只由基座持有与刷新：子应用经 props 获得取 token 的函数引用并注入 `createClient` 的 `getHeaders`，**禁自行持久化 token**；独立运行模式从环境供给层取（十一-2）。
2. 【强制】**401 跳转登录权唯一归基座**（`shouldRedirectToLogin` 对应的导航端口实现注册在基座）；子应用收到 401 只抛 `ApiError` 上报，禁自行跳转。
3. 【强制】子应用全部 HTTP 请求走 `@yarch/contract` http 封装：同一信封解包 / 错误码表 / `X-Trace-Id` 透传（对齐 [../api/rest-response.md](../api/rest-response.md)、[../api/error-codes.md](../api/error-codes.md)、[../api/logging-trace.md](../api/logging-trace.md)，协作参考级）。
4. 【强制】traceId 跨应用延续：子应用复用基座下发的 trace 上下文/生成器，禁各造一套 trace 头——跨应用排障一条链拉通。
5. 【强制】子应用前端错误统一上报基座边界处理（window.onerror/资源错误在基座捕获），上报信息必须含应用名标识。
6. 【推荐】独立运行模式登录态以 mock/开发态注入（环境变量开关）；双模式行为差异只存在于供给层，业务代码零分支。

## 十一、独立运行与集成双模式

1. 【强制】子应用必须可独立 `dev` 起服务、独立 `build` 出产物（不依赖基座存在）。
2. 【强制】双模式差异收敛到**环境供给层**（登录态/路由 base/菜单上下文的来源）；业务代码出现 `if (isMicro)` 分支即设计缺陷——应抽象为端口注入。
3. 【强制】双模式冒烟进 CI：独立构建 + 被基座集成加载两路径都要绿（模板内置，见十三）。
4. 【推荐】独立模式入口提供最小外壳（临时布局/菜单占位）；外壳代码不进集成产物。

## 十二、部署与版本

1. 【强制】子应用独立发版、独立回滚：一次业务变更只发一个子应用；需全体系连坐重发的改动是架构信号，应退回审视边界划分。
2. 【强制】基座维护**子应用入口登记表**（manifest：应用名 → 入口 URL/版本/路由前缀/菜单元数据），入口变更只改此表；表进 git 声明式纳管（对齐 [../infra/nginx.md](../infra/nginx.md) 一-2 配置纪律）。
3. 【强制】构建产物内容寻址（hash 文件名）且旧版本保留：回滚 = manifest 指针回拨，不重发构建。
4. 【强制】静态托管按 [../infra/nginx.md](../infra/nginx.md)：静态目录 `/{应用名}/` 一应用一 root，`try_files` 兜底 index.html 防 history 路由 404。
5. 【强制】路由前缀与事件名是公共契约，破坏性变更走评审并全体系通知；基座禁依赖子应用页面内部 DOM 结构。
6. 【推荐】子应用入口加载失败自动降级到本地缓存上一版本，可用性收益登记后再启用。
7. 【参考】跨环境（test/staging/prod）入口 URL 由环境配置注入，禁硬编码。
