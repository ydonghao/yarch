# RediSearch 开发规约（v1.0 已定稿）

> **状态：已定稿**（2026-09-01 评审通过）。供人阅读、供 AI 作为规范上下文使用。
> 等级：**【强制】**违反即缺陷；**【推荐】**默认遵守、评审后可豁免；**【参考】**正向引导。适用 RediSearch 2.x+（Redis 模块）。前置约束：本规约叠加于 [redis.md](redis.md) 之上，key/TTL/容量纪律全部继承。

## 一、定位与边界

1. 【强制】RediSearch 只做 **Redis 数据就地查询**（二级索引、轻量前缀/数值/地理过滤）；全文检索与复杂聚合归 ES（见 [elasticsearch.md](elasticsearch.md) 一-5 分层）；跨此边界的用法须评审。
2. 【强制】引入索引必须论证：查询模式明确、数据本就驻留 Redis；禁"顺手建索引"占内存。
3. 【强制】共享实例下索引名前缀 = 服务名：`{服务名}:idx:{业务域}`——与 key 前缀规约同构。

## 二、索引设计

1. 【强制】索引 schema 显式声明（`FT.CREATE ... SCHEMA`），字段类型按语义选（TEXT/NUMERIC/TAG/GEO/VECTOR），禁索引全字段。
2. 【强制】索引只覆盖查询条件字段，返回大字段按 key 回取（索引命中 → 取原 key），禁把大 value 复制进索引字段。
3. 【强制】TAG 用于枚举/精确匹配（免分词），TEXT 仅限真正需要分词的场景——过滤字段一律 TAG。
4. 【强制】数据 key 命名与索引 `PREFIX` 对齐（如 `ysaas:iam:user:*`），索引重建以同前缀扫全量为准。
5. 【推荐】索引字段加 `SORTABLE` 仅用于需要排序的字段（内存代价）；可排序字段数控制在个位数。

## 三、查询纪律

1. 【强制】查询语法用户输入必须转义（`@field:(...)`、`-`、`|` 等特殊字符）——注入面与 SQL 同级对待。
2. 【强制】分页 `LIMIT offset num` 总窗口 ≤ 10000（模块默认上限），更深翻页改游标式（按排序键续查）——禁调大上限。
3. 【强制】禁无 LIMIT 的全量查询；聚合（`FT.AGGREGATE`）必须带 `LIMIT` 与分组键基数评估。
4. 【推荐】高频查询用 `FT.PROFILE` 验证计划；查询超时与命令超时对齐 redis.md 五-2。

## 四、内存与生命周期

1. 【强制】索引内存计入实例容量水位（redis.md 八-2 的 70% 治理口径）：索引引入后必须复测内存与 P99。
2. 【强制】索引重建（`FT.DROPINDEX` + `FT.CREATE ...`）走低峰，并保留旧索引切换方案（双索引名灰度）；`DD` 参数（连数据删）禁用。
3. 【强制】随业务下线的索引必须显式 DROP 并登记注销——孤儿索引视为资源泄漏。
4. 【推荐】索引 schema 变更（加减字段）按重建流程管理，变更登记进业务仓。

## 五、运维基线

1. 【强制】监控追加：索引内存占用（`FT.INFO` 巡检）、查询 QPS/P99、慢查询；与 Redis 基线同面板。
2. 【推荐】模块版本随 Redis 版本矩阵验证后升级；自建实例启用模块需在 docker-compose 登记镜像与版本。
