# Nacos 开发规约（v1.0 已定稿）

> **状态：已定稿**（2026-09-01 评审通过）。供人阅读、供 AI 作为规范上下文使用。
> 等级：**【强制】**违反即缺陷；**【推荐】**默认遵守、评审后可豁免；**【参考】**正向引导。适用 Nacos 2.x（注册中心 + 配置中心）。来源见文末附录。

## 一、实例与命名空间

1. 【强制】环境隔离用 **Namespace**：一环境一命名空间（`dev` / `test` / `staging` / `prod`），实例级隔离；**禁止**用 Group 区分环境，**禁止**在 DataID 里带环境后缀替代命名空间。
2. 【强制】多项目共享同一 Nacos 实例时，Namespace 仍按环境划分，项目隔离由 **Group（配置）与服务名前缀（注册）** 承担——Group 即共享实例下的租户边界，与 Redis key 前缀规约同构（见 [redis.md](redis.md) 二-1）。
3. 【强制】创建命名空间时自定义可读的命名空间 ID（如 `prod`，不使用自动生成的 UUID）；客户端配置连接的是**命名空间 ID**，不是名称——ID 一经使用不得变更。
4. 【强制】服务名与部署环境一一对应：同一服务在不同环境注册到对应命名空间，禁跨环境注册。
5. 【强制】注册中心与配置中心共用实例时，命名空间模型必须一致（同环境同 ID），不得注册与配置两套划分。

## 二、服务注册与发现

1. 【强制】服务名 = 应用（服务）名，小写、短横线分隔（`order-service`），与代码仓库名、Redis 前缀、Kafka 前缀保持一致；禁用默认随机服务名。
2. 【强制】注册元数据必带：`version`（Git 短哈希或语义版本）、`env`；可选 `zone` / `weight`。
3. 【强制】消费方按服务名 + 命名空间发现并调用，禁写死 IP:port 直连；框架侧的地址列表缓存必须开启（注册中心故障时可用本地快照）。
4. 【强制】优雅上下线：发布时先反注册（或摘流量）再停进程；启动就绪后再注册（健康检查通过才接流量）。
5. 【推荐】灰度发布用权重或标签路由（元数据打标 + 消费方按标签筛选），禁靠"多注册一个实例"土法灰度。
6. 【推荐】开启保护阈值（如 0.3~0.5）：实例大规模掉线时返回全部实例，防止注册中心推空引发雪崩。
7. 【参考】临时实例（ephemeral，心跳）用于微服务常驻进程；持久实例用于第三方/静态依赖接入。

## 三、配置管理

1. 【强制】三层定位唯一确定一条配置：`Namespace（环境）+ Group（项目/业务域）+ DataID`；三者职责不得混用。
2. 【强制】DataID 命名：`{应用名}-{profile}.{格式}`（如 `order-service-prod.yaml`）；Spring 系按框架默认拼接规则；应用专属配置以应用名开头。
3. 【强制】公共配置与应用配置分离：公共配置 Group 用共享组、DataID 以 `public-` 开头（如 `public-db.yaml`）；应用通过引用（extension-configs / import）聚合，禁到处复制粘贴。
4. 【强制】敏感配置（密码、密钥、凭证）必须加密存储（Nacos 配置加密插件或外部 KMS/Secrets），禁明文入库；账号密码类配置同时禁明文出现在 dataId 名称与描述里。
5. 【强制】生产配置变更必须走灰度验证：先指定实例 Beta 发布，观察后再全量；变更后可回滚（历史版本能力必须可用，定期验证）。
6. 【强制】配置格式统一 YAML（结构化、可注释）；禁把配置当日志或数据存储——单条配置建议不超过 100KB，超限拆分或下沉存储。
7. 【强制】客户端必须启用本地快照兜底：配置中心不可用时以最后一次快照启动，禁"拉不到配置就崩溃退出"。
8. 【强制】配置变更监听回调必须幂等且可失败重试（回调里只做热更新，禁复杂业务逻辑）。
9. 【推荐】配置拆分维度：`{应用}-{env}.yaml`（入口）、`{应用}-{env}-db.yaml`（数据源）、`public-*.yaml`（共享）；禁一个巨型 all-in-one 配置。
10. 【参考】配置项命名 lowerCamelCase，与 RestResponse JSON 字段风格一致。

## 四、权限与运维

1. 【强制】生产实例必须开启鉴权：账号/角色按命名空间授权（RBAC），应用账号最小权限（本项目 Group/服务前缀）；禁匿名读写生产。
2. 【强制】配置与服务的变更审计开启；配置定期导出备份（并纳入仓库存档或备份系统，恢复演练同数据库备份级对待）。
3. 【强制】Nacos 只承担注册与配置，禁作为业务数据的存储或消息通道。
4. 【推荐】监控指标：客户端连接数、配置推送失败、服务订阅数、实例上下线事件、TPS/DAS 类巡检；命名空间配额与容量巡检。
5. 【推荐】升级 Nacos 服务端前先在独立环境演练；客户端与服务端大版本错配矩阵提前验证。
6. 【参考】自建实例加入 yarch 共享基础设施时，以 docker-compose 纳管，与既有中间件同等备份策略。
