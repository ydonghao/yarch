# Redis 开发规约（v1.0 已定稿）

> **状态：已定稿**（2026-09-01 评审通过，纳入 yarch 规约层）。供人阅读、供 AI 作为规范上下文使用。
> 等级：**【强制】**违反即缺陷；**【推荐】**默认遵守、评审后可豁免；**【参考】**正向引导。适用 Redis 6+ / 兼容 Redis 协议的托管服务。来源与口径差异见文末附录。

## 一、场景与部署规约

1. 【强制】每个业务上线前必须明确 Redis 的定位：**高速缓存** 或 **数据存储**，二者不得混用于同一逻辑 DB。
2. 【强制】定位为高速缓存时：业务设计不得强依赖缓存数据完整性（可能被淘汰），淘汰策略用 `allkeys-lru`（或 `volatile-lru` + 全量 TTL），持久化可按需弱化。
3. 【强制】定位为数据存储时：持久化必须开启（AOF `everysec` 起步），淘汰策略必须为 `noeviction`，内存使用率配置告警（建议 70% 水位）。
4. 【强制】多项目共用同一 Redis 实例时，必须以 **key 前缀（命名空间）隔离**（见二-1），前缀即租户边界；有条件时一业务一实例（或一 DB）。
5. 【推荐】业务与 Redis 就近部署（同 VPC/同机房）；公网直连生产 Redis 禁止。
6. 【推荐】DB 编号不承载业务语义（一律用 `db0`，靠前缀隔离）；集群版不支持多 DB，从设计期就不依赖 DB 切分。

## 二、Key 设计规约

1. 【强制】Key 命名格式：`服务名:业务域:实体[:字段][:ID]`，英文冒号分层，首段必须是服务/应用名——这是共享实例下的隔离边界。

```
正例：ysaas:iam:user:10001
      yagent:session:token:a3f8...
反例：user_10001（无服务前缀，共享实例下必冲突）
      ysaas:user:张三（非 ASCII）
```

2. 【强制】Key 用可读字符串，仅小写字母、数字、冒号、下划线、短横线；禁空格、换行、引号及其他转义字符；禁中文。
3. 【强制】Key 长度（含前缀）不超过 128 字节；在完整表达业务的前提下尽量短（高频 key 可用约定缩写，如 `u` 代 `username`，缩写须团队登记）。
4. 【强制】集群架构下，同一命令操作多个 key 时必须用 hash tag（`user:{10001}:profile`）保证同分片；同时评估 hash tag 不引发数据倾斜。
5. 【强制】缓存类 key 必须设置 TTL：显式业务时长 + 10% 以内随机抖动（防同刻集中过期）；默认兜底 TTL 不超过 7 天。禁只增不删、禁不设 TTL 的"永久缓存"。
6. 【强制】Value 大小：String 类型不超过 10KB；超过即重构（压缩、拆分、下沉存储）。
7. 【强制】集合类（Hash/List/Set/ZSet/Stream）元素个数不超过 1000；超限按业务维度拆分为多个 key（如按用户 ID 分桶）。
8. 【推荐】语义上同前缀的批量 key 用固定层级表达，便于 `scan` 按前缀巡检与治理。

## 三、Value 设计规约

1. 【强制】Value 序列化用语言无关格式：JSON / MessagePack / Protobuf；禁存语言原生序列化对象（Java JDK 序列化、Go gob、Python pickle）——阻塞跨栈与版本升级。
2. 【强制】按访问模式选数据结构，不得无脑 String 存 JSON：

| 场景 | 结构 |
|---|---|
| 对象多字段独立读写 | Hash |
| 去重集合 / 标签 | Set |
| 排行榜 / 延迟队列 | ZSet |
| 简单队列 / 最新 N 条 | List / Stream |
| 计数器 | String INCR |
| 判存在 + 过期 | String SET NX |

3. 【推荐】同一对象的 N 个字段禁拆成 N 个 String key——用一个 Hash，省内存（ziplist 编码）且管理集中。
4. 【推荐】大文本、大对象先压缩（如 gzip/zstd）再入 Redis，超过 10KB 压缩后仍超则下沉对象存储，Redis 只存引用。
5. 【参考】精确数值（金额）不走 Redis String 浮点，存整型分值或字符串。

## 四、命令使用规约

1. 【强制】生产禁用阻塞与全库命令：`KEYS *`、`FLUSHALL`、`FLUSHDB`；线上通过 `rename-command` 或云厂商参数将其禁用或改写。
2. 【强制】遍历一律用 `SCAN`/`HSCAN`/`SSCAN`/`ZSCAN`（`count` 建议 ≤500），并处理好游标循环与中途变更；禁 `SMEMBERS`、`HGETALL`、`LRANGE 0 -1` 作用于可能超限的集合。
3. 【强制】禁在客户端做全量轮询拉取；需要变更通知用 keyspace notification 或 Stream，且不得将其当可靠消息（见 12）。
4. 【强制】批量操作用 pipeline：单 pipeline 命令数 ≤100；pipeline 使用独立连接，不与常规命令共用。
5. 【强制】Lua 脚本必须短小、纯内存、O(1)~O(log N)；禁在 Lua 中封装事务、禁大循环；能用原生命令/扩展结构替代的不用 Lua。
6. 【强制】Redis 事务（MULTI/EXEC）不支持回滚——需要原子性的场景用单命令天然原子（`SET NX PX`、`INCR`）或 Lua；禁依赖事务做一致性。
7. 【强制】分布式锁的标准实现：`SET key uniqueValue NX PX <ttl>`，释放必须校验持有者（Lua 比对后 DEL）；锁粒度小、TTL 覆盖业务时长，并用看门狗续期或接受超时放弃。
8. 【强制】禁 `BLPOP/BRPOP` 等长阻塞命令在共享连接池上使用（独占连接）；需要阻塞语义用 Stream + 消费组。
9. 【强制】Pub/Sub 禁承载可靠消息：不持久化、无 ACK；订阅量大（>100 客户端）或消息大（>1KB）时必须换 Stream 或专业 MQ。
10. 【强制】`EXPIRE`/`TTL` 与写入同 pipeline 或同 Lua 提交，禁写后另发一条设置过期（崩溃窗口留无 TTL key）。
11. 【推荐】慎用 `SORT`、`SINTER`/`SUNION` 作用于大集合；`DEL` 大集合改 `UNLINK`（异步回收）。
12. 【参考】`OBJECT ENCODING` 了解编码；Hash/Set 尽量保持 ziplist/listpack 编码（控制元素数与单元素大小）。

## 五、客户端规约

1. 【强制】使用连接池（各栈主流客户端池化实现），禁裸单连接；池大小按 `QPS × P99耗时` 估算并设上限，与 Redis `maxclients` 联动。
2. 【强制】必须设置连接超时与命令超时；命令超时按 P99 制定（缓存场景建议 50~200ms），并区分连接超时/读写超时分别配置。
3. 【强制】重试必须幂等：仅对读命令与明确未执行的写自动重试；重试次数 ≤2、带退避（指数 + 抖动）；超时重试阈值禁设得过短（<200ms 触发重试风暴）。
4. 【强制】客户端必须有容错降级路径：Redis 不可用时缓存类业务降级到 DB + 限流，禁无限重试雪崩。
5. 【推荐】集群客户端开启拓扑自动刷新（cluster topology refresh）；哨兵模式客户端必须走哨兵发现主节点，禁直连主 IP。
6. 【推荐】连接闲置回收与预热；发布前手动触发一次主备切换演练，验证客户端容错（自动重连、读切主）。

## 六、大 Key 与热 Key 治理

1. 【强制】上线前评审 key 设计中的大 Key 风险（口径即二-6/二-7）；新功能上线后一周内用 `redis-cli --bigkeys`（低峰）或云厂商缓存分析复查一次。
2. 【强制】发现大 Key 的治理路径（按序）：拆分（按分桶/字段）→ 压缩 → 下沉存储；删除大 Key 用 `UNLINK`，禁同步 `DEL` 大集合。
3. 【强制】热 Key（单 key QPS 显著高于均值，参考口径 >5000）必须治理：本地进程缓存（短 TTL）→ key 加随机后缀打散（N 份读副本）→ 读写分离/只读副本。
4. 【推荐】高频读取的配置类数据预加载到本地缓存，Redis 只做变更通知源。
5. 【推荐】监控指标至少覆盖：QPS、命中率、内存使用率、连接数、慢查询数、evicted_keys、响应时间 P99。

## 七、缓存一致性规约

1. 【强制】默认采用 Cache-Aside：读→ miss → 回源 DB → 回填；写→ 先更新 DB，再删除缓存（DEL，禁更新缓存）。
2. 【强制】必须设计缓存穿透防御：不存在的 key 也缓存空值（短 TTL 30~60s）或布隆过滤器；入口参数校验先行（与 RestResponse 1001 呼应）。
3. 【强制】必须设计缓存击穿防御：热点 key 过期重建用单飞（分布式锁/单进程 singleflight），期间其余请求返回旧值或短暂等待。
4. 【强制】必须设计缓存雪崩防御：TTL 加随机抖动（二-5），批量预热分批进行；Redis 整体故障时 DB 侧有限流兜底。
5. 【推荐】强一致场景（余额/库存类）不走缓存直读，或用"缓存标记 + DB 权威读"模式；一致性需求写入设计评审。
6. 【参考】延迟双删等进阶策略仅在明确出现脏读事故后引入，不做默认。

## 八、运维基线

1. 【强制】慢日志常开（`slowlog-log-slower-than` 建议 10ms），周期评审；云厂商实例定期查看慢请求与热/大 Key 分析。
2. 【强制】CPU / 内存 / 带宽 / 连接数配告警；内存达到 70% 水位必须治理（扩容或清理）。
3. 【强制】数据存储定位的实例必须有恢复方案：AOF + RDB 双开或云厂商备份策略，并至少每季度演练一次恢复。
4. 【强制】生产实例必须认证（强密码/ACL），禁裸奔端口；禁公网暴露。
5. 【推荐】禁用命令清单（四-1）随实例初始化落地（IaC），不依赖人工记忆。
6. 【参考】压测数据必须带 `test:` 前缀且用后清理；禁止在生产实例做未评估的压测。
