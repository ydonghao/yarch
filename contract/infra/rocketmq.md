# RocketMQ 开发规约（v1.0 已定稿）

> **状态：已定稿**（2026-09-01 评审通过）。供人阅读、供 AI 作为规范上下文使用。
> 等级：**【强制】**违反即缺陷；**【推荐】**默认遵守、评审后可豁免；**【参考】**正向引导。适用 RocketMQ 4.x / 5.x。与 Kafka 的分工见文末附录；来源见附录。

## 一、集群与部署

1. 【强制】生产集群至少 2 个 NameServer（无状态）+ 2 组 Broker 主从（DLedger 自动切换或主从+控制器），单机实例仅限本地开发。
2. 【强制】多项目共享集群：**topic 前缀 = 服务名**隔离，ACL（AK/SK）按前缀授权——与 Redis key、Kafka topic、Nacos Group 的租户边界同构。
3. 【强制】生产 Broker 开启 ACL 鉴权，禁匿名收发；应用账号按前缀最小授权。
4. 【强制】禁用自动创建 topic（`autoCreateTopicEnable=false`），`TBW102` 机制不得作为生产依赖；topic 一律显式创建并登记（见二-5）。
5. 【推荐】4.x remoting 客户端与 5.x gRPC 客户端不混用于同一应用；新应用统一 5.x 客户端。

## 二、Topic 与队列

1. 【强制】topic 命名：`{服务名}.{业务域}.{事件名}`，全小写、点分隔——与 Kafka 规约一致，前缀即租户边界。
2. 【强制】禁占用系统保留名：`%RETRY%`、`%DLQ%`、`SCHEDULE_TOPIC_*`、`TBW102`、`SELF_TEST_TOPIC`、`OFFSET_MOVED_EVENT` 等。
3. 【强制】队列数（read/writeQueueNums）创建时定妥且读写一致；扩队列须评估顺序消息的队列路由影响。
4. 【强制】tag 表达子类型过滤维度（`order.created` / `order.paid`），tag 不承载数据；SQL92 属性过滤慎用（性能成本）。
5. 【强制】topic 清单登记：业务仓 docs 登记 topic 名、属主、tag 集合、保留策略——机制与错误码 3xxx+ 段位、Kafka topic 登记一致。

## 三、生产者

1. 【强制】ProducerGroup 命名 `{服务名}.{用途}`，禁用 `DEFAULT_PRODUCER_GROUP`；一组一用途。
2. 【强制】重要消息同步发送并处理 `SendResult`：非 `SEND_OK` 按业务语义重试或告警，禁"发后不管"。
3. 【强制】消息必须携带：业务键（Keys，幂等与排障索引）、tag（过滤）、用户属性 `traceId`（贯穿 [../api/logging-trace.md](../api/logging-trace.md) 同一条链）。
4. 【强制】开启消息轨迹（messageTrace）用于生产排障。
5. 【强制】事务消息纪律：本地事务与回查必须幂等且可查证（事务/执行日志落库）；回查逻辑必须实现，禁只发半消息不处理回查；事务消息仅用于"本地事务 + 发消息"的原子性，禁当通用分布式事务框架。
6. 【强制】单条消息默认上限 4MB 视为硬边界：超限改引用传递（消息带对象存储 key），禁调大上限塞大对象。
7. 【推荐】延时消息用系统机制（4.x 延时级别 / 5.x 任意延时）；天级以上长延时改调度表方案。
8. 【参考】批量发送仅用于吞吐敏感场景，失败定位按单条兜底。

## 四、消费者

1. 【强制】ConsumerGroup 命名 `{服务名}.{用途}`，与订阅 topic 用途一一对应；**同一 ConsumerGroup 内所有实例的订阅关系（topic + tag）必须完全一致**——订阅关系不一致是 RocketMQ 经典故障（消费丢失/错乱），部署前校验。
2. 【强制】幂等消费是默认假设：至少一次语义下重复必然发生——按业务键（Keys）或唯一索引去重（与错误码 1007、Redis 幂等写、Kafka 规约同源）。
3. 【强制】消费失败交给内建重试通道（`%RETRY%{group}`，默认 16 次指数退避）→ 死信 `%DLQ%{group}`；消费逻辑返回 `RECONSUME_LATER` 交还框架，禁自行 catch 吞掉或本地无限重试。
4. 【强制】死信必须监控告警并闭环处理（人工修复 / 工具重投）；DLQ 消息保留策略纳入治理。
5. 【强制】消费模式默认 CLUSTERING（集群消费）；BROADCASTING（广播）无重试、无堆积语义，仅用于本地缓存刷新类场景，使用须评审。
6. 【强制】消费逻辑必须有时限且不阻塞线程（Push 消费单队列串行），禁单条无限阻塞拖垮消费线程池。
7. 【推荐】顺序消息：发送端 `MessageQueueSelector` 按 sharding key 选队列，消费端 orderly 消费；仅顺序刚需场景使用（吞吐代价），key 选择与业务顺序边界一致（同 Kafka 的 key=顺序边界）。
8. 【推荐】5.x 选用 Pop 消费避免长连接独占队列（按需评估）。
9. 【推荐】消费堆积（差异值）常态监控告警，按业务 SLA 定阈值。

## 五、消息模型与序列化

1. 【强制】消息体跨栈序列化统一 JSON 或 Protobuf（与 Redis value、Kafka 消息体同构），禁语言原生序列化。
2. 【强制】消息 schema 演进只做向后兼容（新增可选字段；禁改语义与类型）；破坏性变更新 topic 或新 tag 子类型。
3. 【推荐】事件契约文档随业务仓维护：事件名、tag、字段、生产者、消费者清单（与 Kafka 事件契约同一份文档体系）。

## 六、运维基线

1. 【强制】监控告警至少覆盖：消费堆积、DLQ 新增、发送 TPS/RT 与错误率、Broker 磁盘水位（70% 治理）、主从切换事件。
2. 【强制】消息保留时间（fileReservedTime）按业务显式设置并评审（默认 72h 仅作起点）；磁盘高水位删旧保护行为必须知晓。
3. 【推荐】Dashboard/控制台与消息轨迹纳入共享基础设施统一部署；定期巡检订阅关系一致性。
4. 【推荐】Broker 与 NameServer 配置变更走评审登记；自建实例以 docker-compose 纳管，与既有中间件同等对待。

## 附：与 Kafka 的分工（选型决策，可推翻）与来源

**双轨分工（2026-09-01 落）：**

| 场景 | 选型 | 理由 |
|---|---|---|
| 在线业务消息：事务消息、延时消息、内建重试/DLQ 的业务命令与通知 | **RocketMQ** | 事务/延时/重试开箱即用，业务消息语义完备 |
| 高吞吐事件流、日志管道、数据集成、Rust 侧生产消费 | **Kafka** | 四栈客户端全一线（rdkafka/franz-go），生态与吞吐 |

同一业务事件双写两个 MQ 需评审（一致性与双消费复杂度）；默认一个事件域只落一个 MQ。

- 客户端纪律（订阅关系一致、Producer/ConsumerGroup 命名、Keys/tag、事务回查幂等、RECONSUME_LATER 语义）：RocketMQ 官方文档「最佳实践」与阿里云 ONS 口径。
- 系统保留 topic、4MB 消息上限、默认 16 次重试、72h 默认保留：RocketMQ 官方文档默认值。
- 命名/幂等/traceId 贯穿/登记机制：与 yarch 既有规约（redis.md、kafka.md、error-codes.md）同构对齐。
